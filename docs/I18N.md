# Internationalization

## Languages

The project currently supports:

* Italian — `it`
* English — `en`
* German — `de`

Italian is the primary and canonical language of the website.

Translation files:

```text
data/i18n/it.json
data/i18n/en.json
data/i18n/de.json
```

---

## Architecture

Internationalization is handled by:

```text
js/modules/i18n.js
```

Localized content is stored separately from the HTML structure in JSON files.

The existing i18n architecture should be preserved while the project content is progressively adapted for Ristorante Incontro Limone.

---

## Language Codes

Use the following language codes consistently:

```text
it
en
de
```

These codes are used by:

* translation files
* language configuration
* language switcher
* JavaScript i18n logic
* document language handling

Do not introduce alternative codes for the existing languages.

---

## Default Language

Italian is the default language.

The canonical translation source is:

```text
data/i18n/it.json
```

English and German translations should preserve the meaning, tone and context of the Italian source.

---

## Translation Structure

All translation files should maintain the same key structure.

Example:

```json
{
  "hero": {
    "title": "...",
    "description": "..."
  },
  "navigation": {
    "home": "...",
    "menu": "...",
    "reservation": "..."
  }
}
```

When a new key is introduced, it should be added to all supported language files.

Do not rename or remove a key in only one language file.

---

## Translation Rules

Translations should not be treated as literal word-for-word conversions.

Translations should preserve:

* meaning
* context
* tone
* hospitality character
* editorial style
* culinary terminology
* calls to action
* location-specific terminology

Restaurant names, brand names and proper names should not be translated unless an established localized form exists.

---

## Content Accuracy

Factual restaurant information must remain consistent across all languages.

This includes:

* restaurant name
* address
* telephone
* email
* opening hours
* menu information
* prices
* reservation information
* location information
* events
* facilities
* restaurant history

Localized content must not introduce unverified facts.

When factual information changes, update the canonical Italian content and all affected translations.

---

## Missing Translations

A missing translation should not be treated as a permanent state.

Where the existing i18n implementation provides a fallback, it may be used temporarily during development.

Missing translation keys should be identified and completed before production release.

Do not leave visible translation keys such as:

```text
hero.title
navigation.menu
reservation.submit
```

in the user interface.

---

## Dynamic Content

Localized text generated or inserted by JavaScript should use the existing i18n system.

This includes, where applicable:

* navigation labels
* buttons
* modal content
* interface messages
* reservation interface text
* gallery labels
* dynamic section content

Avoid hard-coding language-specific interface strings inside JavaScript modules when the same content can be represented through the translation system.

---

## HTML Language

The HTML document should use the appropriate language code.

Default:

```html
<html lang="it">
```

Supported values:

```text
it
en
de
```

When the language changes dynamically, document language handling should remain consistent with the existing implementation.

---

## Language Switching

Language switching is handled through the existing i18n architecture.

The language switcher should:

* clearly indicate the available languages
* preserve the current page state where possible
* update localized content consistently
* update the document language
* remain usable on mobile
* avoid unnecessary page reloads when the existing implementation supports dynamic switching

---

## Persistence

If the existing implementation persists the selected language, the established persistence mechanism should be preserved.

Language state should not be stored independently by multiple modules.

The configuration for language persistence is centralized through the existing project configuration where applicable.

---

## Adding a New Language

Adding a new language requires more than creating a JSON file.

At minimum:

1. Create the new translation file in `data/i18n/`.
2. Preserve the existing translation key structure.
3. Add the language to the i18n configuration.
4. Add the language to the language switcher.
5. Verify all translation keys.
6. Verify document language handling.
7. Test responsive layouts with the new text lengths.
8. Test language persistence if applicable.
9. Review the translated content for quality and accuracy.

Do not add a language by creating only a new JSON file.

---

## Translation Quality

Translations should be reviewed for:

* grammatical correctness
* natural phrasing
* cultural context
* hospitality terminology
* culinary terminology
* consistency
* correct calls to action
* appropriate text length

Italian remains the reference language for intended meaning and factual content.

---

## Responsive Considerations

Translations may be longer or shorter than the Italian source.

The interface must therefore accommodate variable text lengths.

Avoid:

* fixed-width text containers
* hard-coded line breaks
* text truncation without a clear reason
* layouts dependent on a specific word length

Test localized content on:

* desktop
* tablet
* mobile

---

## SEO and Metadata

Where localized SEO metadata is supported, translations should also cover:

* page title
* meta description
* Open Graph text
* relevant structured content

Localized metadata must remain factually consistent with the canonical Italian content.

Do not translate URLs, coordinates or other technical values unless the implementation specifically requires it.

---

## Development Workflow

When adding or changing localized content:

1. Update the Italian source content.
2. Verify the factual information.
3. Update English.
4. Update German.
5. Check translation key consistency.
6. Test language switching.
7. Check desktop and mobile layouts.
8. Check modals and dynamic content.
9. Verify SEO metadata where applicable.

---

## Synchronization Rule

All supported translation files should remain structurally synchronized.

Before committing changes, verify that the translation keys exist consistently across:

```text
data/i18n/it.json
data/i18n/en.json
data/i18n/de.json
```

The JSON structure is part of the application interface and should not be changed casually.

---

## Source of Truth

The actual translation files and the implementation in:

```text
js/modules/i18n.js
```

are the source of truth for the current internationalization system.

This document describes the rules for maintaining that system.

When the i18n architecture changes, update this document accordingly.
